# verifact 设计文档

> 事实哨兵：把文档里的硬数字绑定到产出物上，漂移即红。
> 版本：0.1.0（2026-09-29）
> 位置：fibemate-tools/verifact/

---

## 一、问题：文档里的数字会漂移

任何有硬数字的项目都会遇到同一类问题：

- 性能基准写在 README 里，代码在三个月后重测，数字开始各走各的
- 测试计数在 CI 里是 36，文档里是 61（合并重构后未更新）
- 一个「提升 15-31x」的声明，底数来自一个已经不存在的版本
- 头条数字 `p95=78.5ms` 挂在最显眼的位置，但产出物里找不到来源

**这些不是「文档说谎」——是「文档写于某时刻，产出物在另一时刻」。**

人工核对靠 grep 和肉眼。**fibemate 主仓 341 份文档、2251 条声明**——每轮发稿前肉眼扫一遍不现实。

verifact 占的位置：**把「文档声明 vs 产出物」的比对从人工变成自动化门禁。**

---

## 二、核心设计：六态判定

三阶段流程：

### 阶段 1：抽取

扫描 markdown（默认只扫代码块外的正文），把带单位的数字连同键名抽出来。

- 输入样例：`103µs`、`26,115 states`、`654 行`
- 每条声明记录：`{file, line, key, value}`

### 阶段 2：绑定

把声明和产出物对接。产出物来源在 `verifact.json` 里登记：

- benchmark 的 JSON / 日志
- 主仓 scripts
- 时间戳目录
- 核心库

绑定按**键名相似度**和**数值容差**打分（默认阈值 `minScore: 0.45`，相对容差 0.5%）。

### 阶段 3：判定

六种结果，**只有一种是红的**：

| 判定 | 含义 | 处置 |
|:--|:--|:--|
| `verified` | 文档值和产出物在容差内一致 | 绿 |
| **`drift`** | 绑定成功但数值超出容差 | **红，门禁拦截** |
| `ambiguous` | 多个产出物候选冲突，或跨模块同名键 | 交人工 |
| `unbound` | 找不到产出物依据 | 交人工 |
| `引用存在` | 声明引用 `lg-XXX` 等实体，在扫描范围内找到 | 绿 |
| `引用缺失` | 同上，但找不到 | 交人工 |

## 三、设计决策：为什么不把 `unbound` 当错

**这是本工具最重要的一个立场。**

如果把 `unbound` 也算失败——工具会在第一天就被噪音淹没。

`unbound` 1836 条不等于文档在说谎：
- 可能证据没导出成机器可读格式
- 可能是叙述性文字（「我们做了 X」）
- 可能是外部引用（论文、标准）

**红只留给一种情况：找到了依据，但数字对不上。**

这个分层的关键是：**「没证据」≠「错」。** 把两者混为一谈的工具，会在用户第一次看报告时就失去信任。

同理：`ambiguous` 也不红——多个候选冲突时，机器不知道该信谁，交人工。

---

## 四、设计决策：为什么不用 AST

**零外部依赖。** 扫描是正则 + 字符串匹配，不引入 acorn / esprima / 任何解析器。

**取舍逻辑**：
- 完整 AST 意味着「我理解了语义」的承诺——这个承诺给不起
- 掩码扫描（字符串匹配）是启发式，会漏掉混淆写法，也可能被字符串里的巧合命中
- **这些局限写在 README 的「已知局限」一节，不藏在脚注里**

**代价明码标价**：漏报的代价由「人是最后一道闸」兜底，误报的代价由「判决权在人手里」兜底。

**定位透明的好处**：每条 finding 的 `file` 和 `line` 都是真实的，人工复核直接跳到那行。

## 五、ignore 与 deny：把「口径差异」和「真过期」分开

**问题**：同一个数字，两份产出物各说各话——不是「文档错」，是「口径不同」。

例子：
- 文档引的是 JS 基准（2026-07-18 实测）
- verifact 查到的是硬件基准（FPGA 最新数据）
- **两套数据都对，只是测的东西不同**

**解法**：配置里 `ignore` 和 `deny` 两段，人工复核后的沉淀。

```json
{
 "ignore": [
 { "file": "**/PQC_MIGRATION_PLAN.md", "key": "kem-keygen", "kind": "measure",
 "note": "JS 估算值 vs 硬件基准，口径不同。TODO: 修绑定指向 JS benchmark" }
 ],
 "deny": [
 { "file": "**/TECHNICAL-VERIFICATION.md", "key": "rsa-2048",
 "note": "RSA 对照列，不与 ML-KEM keygen 比对" }
 ]
}
```

**每条带 note，说明为什么。** ignore 不是掩盖——是**把「口径差异」和「真过期」分开登记**。

### 处置分类（dispositions）—— 区分「没有证据」与「不适用证据」

`ignore` 解决的是「同一条声明、两种口径」，它回答不了另一个问题：**这个数字压根不是产物属性**。
清单进度（`0/28`）、一次性测量（`7.8µs`）、实验参数（`n=40, q=1009`）都属于后者 ——
硬把它们绑到静态产物上，只会逼作者写出假绑定。

于是增加一层**处置分类**（RFC: `../docs/rfc-verifact-dispositions.md`，2026-10-26 合并）：

| disposition | 必填参数 | 含义 | 进覆盖率分母 |
|:--|:--|:--|:--|
| `code-artifact` | 无 | 默认，今天的全部行为 | 是 |
| `measured-once` | `artifact=` | 某次运行的测量值 | 否 |
| `progress` | `owner=` | 清单/看板的进度统计 | 否 |
| `narrative` | `why=` | 实验参数、描述性数字 | 否 |

写法是 HTML 注释（GitHub 渲染不可见），三种作用域：文件级（前 5 行）、区域级（`begin`/`end` 成对）、单条级（行尾或紧邻上一行）。

三条硬规则，缺一即**报错**：

1. 非 `code-artifact` 必须指名「谁拥有这个数字」，否则就是无主数字；
2. **只有 `owner` 可以继承**（区域内单条 `progress` 可省略），`artifact` / `since` / `why` 必须就地写；
3. 声明写错 = **整次运行失败**，不是记一条 `docScanError` 就放过 —— 后者会让整份文档的声明静默消失，报告少了一片数字却仍然绿。

报告**永远并列打印两个分母**：`7.0% (code-artifact 285 条)` 与 `7.0% (全部受判 285 条)`。
换了分母的「覆盖率上升」不算上升。

## 六、边界（不做什么）

- **不调 git**——声明绑定的是文件当前状态，不追溯「这个数字在哪个提交改的」（那是 crypto-time-machine 的活）
- **不自动修文档**——只报问题，不改内容。verifact 是指纹比对，不是内容审查
- **`unbound` 不等于说谎**——缺证据只交人工，不进门禁
- **绑定阈值是经验值**——`minScore: 0.45` 和容差按 fibemate 项目调的，换仓库要重新调
- **无出站网络**——全部扫描和比对在本机完成；`serve` 起的看板只监听 `127.0.0.1:8787`
- **写入边界**——只写 `--out` 指定的路径和 `.verifact/` 缓存目录；扫描显式跳过 `.git/`、`node_modules/`

## 七、在 CI 里的用法

主仓 `sentinel.yml`：

```yaml
- name: Run verifact
 working-directory: .sentinel-tools/verifact
 run: node bin/verifact.js verify --docs ../../fibemate/www/docs --fail-on drift --no-cache
```

- 双仓 checkout（主仓 + fibemate-tools）
- `--no-cache` 保证每次全量，不吃缓存红利
- `--fail-on drift` 把红锁定在唯一一种该红的判定上

比成功，CI 绿；比出 drift，CI 红——**不让你合**。

## 八、实测数据（2026-09-27）

对 fibemate 全仓 + 待发布文章 + benchmark 产出物跑全量：

```
文档 341 份 产出物 5369 条 声明 2251 条
verified 145 drift 24 ambiguous 227 unbound 1836
引用型 19（存在 17 / 缺失 2） 另有 17 条声明经 ignore 规则收敛
核验率 7.2%
耗时 4.1s（workers=6，冷缓存）
```

**核验率 7.2% 是诚实的上限**：能自动核验的前提是产出物机器可读。大多数声明（叙事、对比、非数值）没有对应格式。

**工具的作用是守住有依据的那部分，不是假装能核全部。**

## 九、抓到过什么

投产后实际拦下的：

1. **头条数字无出处**——`p95=78.5ms` 出现在主仓 README 和官网 pqc-readiness、FAQ、architecture 四处，产出物里无依据
2. **15-31x 性能声明的底数漂移**——`PROGRESS.md` 的 103µs 对不上产出物的 262μs，倍数声明跟着动摇
3. **TLA+ 不变式 3 vs 7**——发布物和模型文件各说各话
4. **lg-079 引用缺失**——两个文档副本指向同一份本地查不到的时间戳实体

用语线索单独说：抽取器顺带查绝对化措辞，今天的 high 级 5 条：「全球唯一」「绝对安全」「零风险」。这类词在任何审计语境都站不住。

## 十、为什么要公开这份设计

**这个问题不限于 fibemate。**

任何有硬数字的项目——性能基准、测试计数、状态数、文件行数——都可能遇到「文档写于某时刻、产出物在另一时刻」的漂移。

**「不把没证据当错」的六态判定**是一种设计立场：
- 比「一切不匹配皆失败」的工具更实用
- 比「只在明显错误时才报」的工具更主动
- 把「机器能做的」和「必须交人做的」明确分开

如果这份设计对别的项目有帮助——或者你觉得有改进空间——欢迎在 issues 讨论。
