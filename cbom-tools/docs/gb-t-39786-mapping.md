- **Subject:** `cbom-tools compliance` 输出的三项判定（算法强度 / 硬编码风险 / 加密存储边界）
- **Target standard:** GB/T 39786-2021《信息安全技术 信息系统密码应用基本要求》，**第三级**（第 8 章）
- **Related:** [compliance-methodology.md](compliance-methodology.md)、[ADR-0001 置信度模型](adr-0001-confidence-model.md)

## 0. 一句话结论

> `cbom-tools` 能为第 8 章里的 **算法选择** 与 **密钥材料存放位置** 提供“名称级、文件级”的输入证据；
> 它对 **协议是否真的启用、字段是否真的加密、产品是否持证、管理是否有制度** 一律不发言。
> 所以它最多能填密评证据链中的一小段，**且必须与人读配套**。

这也正是本工具在报告里恒写「无法判定」的原因——`无法判定` 不是客气的通过，是「没看」。（见 methodology §3.3）

## 1. 标准结构（第三级）

第 8 章分 8 个条款组，前 4 组是技术要求，后 4 组是管理要求：

| 条款 | 名称 | 本工具相关性 |
|---|---|---|
| 8.1 | 物理和环境安全 | **无**（门禁/视频，非代码） |
| 8.2 | 网络和通信安全 | 部分（算法选择） |
| 8.3 | 设备和计算安全 | 部分（算法选择、日志/程序完整性调用点） |
| 8.4 | 应用和数据安全 | **主要落点**（传输/存储机密性与完整性、不可否认性） |
| 8.5 | 管理制度 | 极弱（仅密钥管理制度与硬编码发现可互为参照） |
| 8.6 | 人员管理 | **无** |
| 8.7 | 建设运行 | 弱（密钥体系与生存周期，仅作输入） |
| 8.8 | 应急处置 | **无** |

第三级技术要求的关键词：**8.2 / 8.3 / 8.4 中的机密性、身份鉴别多用「应」，完整性多用「宜」**。这个「应/宜」差别不是修辞——它是密评里「不符合」与「可改进」的分界。静态工具无法判断一条要求是否被满足，只能指出「代码里有没有这个能力」。

## 2. 三项判定 → 条款映射

图例：**●** 可作为输入证据（工具确实看得到）｜**◐** 仅线索（需要人读或动态验证补齐）｜**○** 不适用（工具原理上做不到）

### 2.1 算法强度（`strength`）

| 条款 | 要求（转录） | 判定 | 工具实际能说什么 |
|---|---|---|---|
| 8.2 a) | 应采用密码技术对通信实体进行身份鉴别，保证通信实体身份的真实性 | ◐ | 代码里出现了哪些算法名（SM2/RSA/ECDSA…）；**不能**说明双向认证是否启用、证书链是否校验 |
| 8.2 c) | 应采用密码技术保证通信过程中重要数据的机密性 | ◐ | 是否存在 TLS/国密 SSL 的调用点与算法名；**不能**说明强制 HTTPS、套件顺序、降级保护 |
| 8.3 a) | 应采用密码技术对登录设备的用户进行身份鉴别 | ◐ | 同上，名称级 |
| 8.3 b) | 远程管理设备时，应采用密码技术建立安全的信息传输通道 | ◐ | 是否有 SSH/TLS 客户端依赖；**不能**说明配置强度 |
| 8.4 a) | 应采用密码技术对登录用户进行身份鉴别 | ◐ | 口令散列用的是 SM3/PBKDF2/bcrypt 还是 MD5；**不能**说明认证流程是否防重放 |
| 8.4 d) | 应采用密码技术保证重要数据在**传输**过程中的机密性 | ● | 传输层加密调用的算法清单 |
| 8.4 e) | 应采用密码技术保证重要数据在**存储**过程中的机密性 | ● | 存储层加密调用的算法清单 |

**这一类最强的产出不是「合规」，而是「不合规的明确信号」**：出现 MD5 / SHA-1 / DES / RC4 / RSA-1024 之类名称时，可以确定与「采用国家密码管理部门核准的商用密码算法」存在张力；反过来，出现 SM4 也**不能**推出合规——参数、模式、密钥管理都在工具视野之外。

### 2.2 硬编码风险（`hardcoded`）

| 条款 | 要求（转录） | 判定 | 工具实际能说什么 |
|---|---|---|---|
| 8.4 e) | 重要数据存储机密性 | ◐ | 代码里出现 PEM 私钥块或高熵密钥串 → 说明「密钥材料进入代码仓库」，这直接削弱存储机密性 |
| 8.7 b) | 应根据密码应用方案，确定系统涉及的密钥种类、体系及其生存周期环节（各环节参照附录 B） | ◐ | 硬编码点可作为「密钥生存周期缺失」的线索 |
| 8.5 b) | 应根据密码应用方案建立相应密钥管理规则 | ◐ | 同上，属反证材料，不是结论 |

**这一类必须写清三条局限**，否则报告会被当成误报合集：

1. **分不清测试向量、公钥与生产私钥**——加密库里大量「密钥状」常量是 KAT 向量；
2. **公钥硬编码本身不违规**（证书/公钥固定是常见做法），只有私钥/对称密钥进入代码才是问题；
3. **看不到运行期来源**——密钥是否来自 KMS/HSM、是否轮换，静态扫描一律无解。

工具当前的做法是只报「疑似」，并在报告 §6 里把命中点逐条列出供人判读；这是有意的保守，不是能力缺陷的掩饰。

### 2.3 加密存储边界（`storage`）

| 条款 | 要求（转录） | 判定 | 工具实际能说什么 |
|---|---|---|---|
| 8.4 e) | 重要数据存储机密性 | ◐ | 存储层（DB/文件/对象存储）附近**有没有**加密调用 |
| 8.4 g) | 宜采用密码技术保证重要数据在**存储**过程中的完整性 | ◐ | 有没有 MAC/签名校验调用点 |
| 8.3 e) | 宜采用密码技术保证日志记录的完整性 | ◐ | 日志写入路径上有没有 HMAC/签名 |

这一项的判定在方法论里恒为 **`无法判定`**：静态扫描看不到数据流，也就无法回答「哪些字段被加密了」。报告只能陈述「在 X 处看到了加密调用，在 Y 处没有看到」，把「没有看到」和「没有加密」严格分开写。

### 2.4 明确不适用（不要在这四项上引用本工具）

| 条款 | 为什么不行 |
|---|---|
| 8.1 物理和环境安全（a–e） | 门禁、视频、机房——与代码无关 |
| 8.2 f) / 8.3 g) / 8.4 i) 密码服务合规 | 需要服务资质与认证状态，不是代码属性 |
| 8.2 g) / 8.3 h) / 8.4 j) 密码产品应达 GB/T 37092 二级及以上 | 需要**产品认证证书**。算法名合规 ≠ 产品合规，这是最容易混淆的一条 |
| 8.5 a) c) d) e) f) 制度与记录 | 制度文本与执行记录，非代码 |
| 8.6 / 8.8 人员与应急 | 同上 |
| 8.7 a) c) d) 方案、建设、投运前评估 | 过程性证据 |

## 3. 第四级：为什么不逐条映射

第四级是第 9 章，条款组结构与第三级一一对应（9.1 物理和环境 … 9.8 应急处置），差异方向是**「宜」收紧为「应」、并要求更长的留存与更强的证据**。

本文件**不逐条引用 9.x 正文**，原因很直接：我手上的公开转录只覆盖到第 8 章，9.x 的逐字内容没有可靠来源。凭结构相似去推断具体措辞，就是给国标编条文——这类错误在对外材料里一旦出现，整份文档的可信度归零。

**做法**：需要第四级映射时，先取得标准正文，再按 §2 的同一张表重做一遍；本文件的三栏结构（条款 / 判定符号 / 工具能说什么）可以直接复用。

## 4. 三栏对照的用法（给写报告的人）

1. **先写「看了什么」**：扫描根目录、文件数、工具版本、CBOM 规格。密评专家第一个问题不是「你发现了什么」，而是「你的覆盖面是什么」。
2. **只写工具看得到的**：算法名、调用点、疑似密钥材料的位置。
3. **把「没看到」写清楚**：`无法判定` 不是结论，是边界声明。写「未在代码中发现存储加密调用」而不是「未加密」。
4. **不写分数、不写等级、不写「符合第 X 级」**。
5. **每条结论都要能被复核**：给出文件路径与行号（工具已输出），否则等于不可验证。

## 5. 对外口径（硬约束）

- 可以说：**「密评辅助工具」「自查报告」「参考方法学」「CBOM 资产清单」**。
- 不可以说：**「符合 GB/T 39786 第三级」「通过密评」「国家级认证」「替代测评」**。
- 报告页眉已固定写明：*「不是密评结论，不产生分数，也不能作为通过测评的证据」*（见 `cbom-compliance.cjs` 的 `renderMarkdown()`）。
- 引用本文件时，必须连同 §0 与 §2.4 一起引用——只截表格不截边界，就是把工具说成了测评机构。
